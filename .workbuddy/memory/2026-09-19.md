- 项目本质：JC2001 软件工程课程 AI 组 9 的作业 —— 校园二手交易平台 PoC（单机 Web 应用）。
- 技术栈：Flask 2.3.3 + Werkzeug + SQLite（data.db）+ 原生 HTML/CSS/JS，无前端框架、无 ORM；图片存 uploads/ 本地目录。

## 在线化 / 去本地依赖 可行性分析（未动手，仅评估）
- 代码实测：23 个路由（21 个 API）、29 处 `conn.execute`、70 个 `?` 占位符、17 处 session、
  47 处 jsonify；SQLite 特有写法极少——6 个 AUTOINCREMENT、1 处 `sqlite3.Row`、1 处 `lastrowid`、
  1 处 `IntegrityError`、4 处 LIKE；`PRAGMA foreign_keys` 未开启（外键实际未强制，迁库要先清孤儿数据）。
- 结论：换在线库可行性 90–95%。最省力是 **Turso/libSQL**（保持 SQLite 方言，只换驱动）；
  最标准是 **PostgreSQL**（Supabase/Neon），代价是 70 个占位符改 `%s`、LIKE→ILIKE、
  `lastrowid`→`RETURNING id`、`sqlite3.Row`→`dict_row`、`IntegrityError`→`UniqueViolation`、补连接池。
- **比数据库更硬的两个坑**：① `uploads/` 是本地磁盘，PaaS 容器文件系统重启即清空 → 必须换对象存储
  （S3/R2/Supabase Storage），且 `/uploads/<filename>` 要改成签名 URL 或代理路由；
  ② `api.js` 的 fetch **没有 `credentials: 'include'`**，前后端分离部署时会丢 cookie 导致登录态失效。
- 其他：`app.secret_key` 硬编码需改环境变量；MySQL 的 CURRENT_TIMESTAMP 时区会让前端 `timeAgo`
  显示错乱（前端按 UTC 解析）；`price` 用 REAL 建议改 NUMERIC。
- 去 Flask 依赖：PyInstaller 打包（README 已有说明）90% 可行但仍是单机；stdlib 重写 http.server
  仅 30% 值得（要手写路由/multipart/会话签名）；真正解是部署到 PaaS。
- **真正的成本驱动是架构**：29 处 SQL 全内联在路由里，没有数据访问层。先抽出 DAL，之后换库才是局部改动。
- 追加结论（用户担心 .bat 限制 macOS、想免装即用 + 数据实时共享）：
  - `.exe` 方案对 macOS **更糟**：PyInstaller 不能交叉编译，要在 macOS 上单独打包；且仍是单机、不共享数据。
  - 当前 `start.bat` 只是 `python app.py` 的包装，macOS 直接 `python3 app.py` 即可跑，不存在"被 bat 锁死"。
  - 要同时满足「任何人免安装 + 一个网址 + 多人共享同一份数据」，**必须有一个常驻托管环境 + 统一数据源**，这是硬约束。
  - 最省改动的路线：托管到**有持久磁盘**的主机（PythonAnywhere 免费版就有，SQLite 与 uploads/ 都能存活）→ 代码几乎零改动。
  - 更标准：PaaS（Render/Fly）+ 托管 Postgres(Neon/Supabase) + 对象存储 → 需先做上面的迁库改造。
  - 注意：**当前代码并没有真正的轮询**（README 写的是 polling，实际只在打开会话/发送后拉取）。要"实时"需在 main.js 加 `setInterval`，后端零改动。
  - 部署前必须换掉 `app.run(debug=True)` 开发服务器 → gunicorn/waitress；SQLite 下 worker 只能给 1，否则 database is locked。
- **免费额度实测核对（2026-09 联网确认，政策会变，落地前需复查）**：
  - **PythonAnywhere Beginner（免费）**：`用户名.pythonanywhere.com`、**512MB 持久磁盘**（SQLite 与 uploads/ 都能长期存活）、
    1 个 web app、1 个 web worker、100 CPU 秒/天、外网白名单、无自定义域名。**不按空闲休眠** →
    免费方案里最贴合「即开即用 + 长期保存」，且代码几乎零改动。
  - **Render 免费 Web Service**：15 分钟无流量休眠，冷启动 30–60 秒；磁盘临时，**重新部署即丢**；持久磁盘是付费项（$0.25/GB/月）；常驻 $7/月。
  - **Render 免费 PostgreSQL：30–90 天后过期并删除数据**（不同来源口径不一，但都会删）→ 绝对不能用来存要长期保留的数据。
  - Neon 免费：0.5GB，空闲 5 分钟挂起（冷启动 0.5–2 秒），**数据长期保留不删**。
  - Supabase 免费：500MB + 1GB 文件存储，**7 天不访问暂停**（需手动唤醒），数据保留。
  - Turso 免费：5–9GB、**不休眠**、SQLite 方言 → 改动最小的在线库。
  - 结论：要「即开即用」就得避开会休眠的免费 Web 实例；要「长期保存」就得避开会过期的免费数据库。
    两个都想要且零成本 → PythonAnywhere；接受每月 $4–7 → 小 VPS / Render Starter 上持久卷最省心。

## 方案 B 落地：仓库改造为「可部署」（已完成并验证）
- 用户选择方案 B（免费 + 更像正式应用），期限要求「维持到 1 月初」。
- **推翻了 Turso 路线**：Turso 已弃用旧的 `libsql-client`，替代品 `libsql`（Rust 原生扩展）在 Windows
  上的支持不明确（sqlalchemy-libsql 文档写"仅 Linux/macOS"）→ 改用 **PostgreSQL(Neon)**，驱动用 psycopg3。
- 新增文件：`config.py`（环境变量配置）、`storage.py`（本地磁盘 / S3 兼容双后端）、`wsgi.py`、
  `Procfile`、`render.yaml`、`.env.example`、`migrate.py`（SQLite→PG 搬数据 + 重置 identity 序列）、
  `sync_uploads.py`（把 uploads/ 推进桶）、`backup.py`（全量导出为带时间戳的 SQLite 文件）、
  `smoke_test.py`、`start.command`（macOS 双击启动）、`DEPLOY.md`。
- **核心设计**：`models.py` 变成方言适配层，`app.py` 里 29 条 SQL **一行未改**。
  规则：`?`→`%s`（跳过引号内的字面量）、`LIKE`→`ILIKE`（对齐 SQLite 的大小写不敏感行为，
  否则搜索会静默退化）、INSERT 自动补 `RETURNING id` 以兼容 `lastrowid`、
  行值归一化（datetime→UTC 字符串、Decimal→float，保住前端既有的时间解析与 jsonify 契约）。
  `DATABASE_URL` 为空即走原生 SQLite，**本地零依赖、行为完全不变**。
- 统一 `IntegrityError`（sqlite3 → psycopg）、`SECRET_KEY`/`HOST`/`PORT`/`DEBUG` 走环境变量，
  启动时打印后端与存储信息并对默认密钥/易失磁盘告警。`debug` 默认改为 False（安全），
  auto-reload 需 `FLASK_DEBUG=1`。
- **回归验证**：`smoke_test.py` 15 项全通过；playwright 全流程 17 张截图通过，仅剩未登录时的
  预期 401。中途抓到并修掉一个真实回归：模块名与实例名都叫 `storage` 导致 `storage.serve`
  AttributeError → 实例改名 `file_store`。
- 未改动后端接口契约与数据库结构（SQLite DDL 与原来逐字一致）。
- 遗留：本机 5000 端口被一次误启动的旧进程僵尸占用（查不到 PID 但仍在应答旧代码），
  已改用 5050 提供预览；彻底清除需重启系统。用户自己的 `start.bat` 在重启后不受影响。
